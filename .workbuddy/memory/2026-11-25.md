## M5 收尾：可发布，但没发布（同日再晚）

**做了什么**
- `scripts/validate-content.mjs`：用 `vite.createServer({middlewareMode:true}) + ssrLoadModule` 读 TS 数据跑校验，不引入 ts-node/tsx。除 `validateContent()` 外还校验**主线 beat 必须真的挂在对应流程里**。

- 分包改成函数式 `manualChunks`（Vite 8 / rolldown 不接受对象式）：`react` 63K / `xyflow` 86K / 内容 58K（gzip）。
- `public/favicon.svg` + `public/og.png`（1200×630，用 `/tmp/og.html` 无头截图生成）；`index.html` 补 OG/Twitter meta。
- `README.md`（含 3 张截图）+ `docs/screenshots/01..04`（1440×900）。
- `.github/workflows/deploy-pages.yml`：**只留 workflow_dispatch**，push 不会自动上线；注释里写了怎么打开 push 触发。

**子路径实测**
`cp -R dist/* /tmp/site/sap-map/` + `python3 -m http.server 4300` → `http://127.0.0.1:4300/sap-map/#/p/wm.inbound` 正常落到 L2，资源相对路径无 404。这条验证了 GitHub Pages 的项目站点场景。

**这一轮最大的教训（工具层，不是代码层）**
排查了半小时"页面空白"，最后发现不是代码问题，而是**开发服务器已经死了**：
之前用 `(npx vite ... &)` 起服务，父 shell 结束进程就被回收；`curl` 在同一条命令里还能 200，下一次调用就 000。
同时 Chrome 在这个沙箱里 `sandbox initialization failed` → network service 反复崩 → 所有导航 ERR_CONNECTION_REFUSED。
正确做法：
- 服务必须用 `run_in_background: true` 的任务方式起，才会在整个会话里活着；
- Chrome 必须加 `--no-sandbox` 才能在这个环境里跑（否则 network/GPU 进程全崩）。

**状态**：`npm run build` 绿，dist 772K / gzip 216K，未部署任何线上地址。

## M6：交互修复 + 对象反查与影响面（2026-11-25 凌晨）

**P0 三个实测问题**

**P1 反查与影响面**
- `usagesOfObject` / `summarizeUsage`：由 `step.objectIds × processesOfStep` 派生，**不加内容字段**。
- 抽屉：引用统计 + 「被引用于」逐条跳转 + 「在图上查看影响」。

- 影响面视觉：只改透明度 + 描边，不重排（保住空间记忆）。

**踩到的坑**
- 同一步骤 id 在多个流程里复用：`下一处` 的索引必须同时比对 `stepId` 与 `processId`，只比 stepId 永远停在 1/3。
- 从搜索打开对象再进影响面，当前选中步骤可能不引用它 → 会"全暗无高亮"。入口处判断，不匹配就先 goStep 到第一个落位。
- 进入影响面必须清 hover，否则残留浮层正好盖住高亮卡。
- 这个环境里 Chrome 页面 `visibilityState=hidden`，CSS 动画会停在第一帧（抽屉 `opacity:0`）、rAF 不推进。截图验收必须注入 `animation:none` 并等 2.2s 以上；否则会误判成"背景透明/布局坏了"。
